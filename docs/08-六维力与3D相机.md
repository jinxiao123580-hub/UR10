## 1.2 RDT：实时数据流协议（实测打通）

Net F/T 实时数据走 **UDP 49152**，协议叫 **RDT (Raw Data Transfer)**：

**① 启动流**——发 8 字节命令：

```
12 34 00 01 00 00 00 00
│  │  │  └─ 采样数（每包几个样本，0=停止）
│  │  └──── 命令字节 0x00
└──┴─────── 固定头 0x1234
```

**停止流**：把采样数改成 `00` → `12 34 00 00 ...`

> 💡 **踩坑记录**：一开始按想当然试了 `cmd=0x01`、`0x02`，全都收不到数据。
> **实际能用的只有 `0x00` + 采样数**。协议文档没在手边时，**穷举比猜快**——
> 见 `scripts/` 里的探测思路：把候选命令挨个发一遍，看哪个开始回包。

**② 收数据**——每个包 **36 字节 = 9 个大端 int32**（实测逐字段对过 HTTP 快照）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `rdt_sequence` | RDT 包序号，**每包 +1** |
| 4 | `ft_sequence` | 传感器内部采样序号（高速率递增） |
| 8 | `status` | 状态字，**0 = 健康**；bit0~5 = Fx/Fy/Fz/Tx/Ty/Tz **饱和**标志 |
| 12 | `Fx` | 力，counts |
| 16 | `Fy` | 力，counts |
| 20 | `Fz` | 力，counts |
| 24 | `Tx` | 力矩，counts |
| 28 | `Ty` | 力矩，counts |
| 32 | `Tz` | 力矩，counts |

**换算**：`物理量 = counts / counts_per_*`（本机 1000000，所以 `3777409 counts = 3.777 N`）。

实测读到的数据：

```
  Fx(N)      Fy(N)      Fz(N)      Tx(Nm)     Ty(Nm)     Tz(Nm)   状态
      3.749      5.780     62.359     2.2609     2.3593     0.2670   正常
      3.780      5.734     62.212     2.2633     2.3533     0.2677   正常
```

> 与 HTTP 快照的 counts 逐项一致（Fx 3777409 ↔ RDT 3819762，同一量级同趋势），
> 说明**字节布局解析正确**。这是验证协议解析的通用手法：**跟设备自带的显示页对照**。

## 1.3 ROS 2 驱动：`scripts/ati_netft_node.py`

**命令行看数**（不依赖 ROS，先确认硬件通）：

```bash

```

```bash
python3 scripts/ati_netft_node.py --ros-args -p ip:=192.168.1.2 -p rate:=200 -p frame_id:=ft_sensor
```

实测输出：

```bash
$ ros2 topic hz /ft_sensor/wrench
average rate: 200.009        # 稳定 200Hz

$ ros2 topic echo /ft_sensor/wrench --once
header:
  stamp: {sec: 1789019986, nanosec: 609952331}
  frame_id: ft_sensor
wrench:
  force:  {x: 3.806902, y: 5.719047, z: 62.281844}
  torque: {x: 2.262586, y: 2.360681, z: 0.265941}
```

| 接口 | 说明 |
|---|---|
| 话题 `/ft_sensor/wrench` | `geometry_msgs/WrenchStamped`（力 N、力矩 N·m） |
| 服务 `/ft_sensor/tare` | `std_srvs/Trigger`，软件去皮（只影响本节点输出，**不改传感器**） |
| 参数 `ip` / `rate` / `frame_id` / `counts_per_force` / `counts_per_torque` | 见 `--ros-args -p` |

**置零（重要）**：

```bash
ros2 service call /ft_sensor/tare std_srvs/srv/Trigger
```

装好工具后**必须置零**，否则测到的是工具自重（本机现在就是 Fz≈62N 这个状态）。
想永久置零（连 HTTP 页和别的程序也生效），在 `setting.htm` 里设置 Software Bias Vector。

## 1.4 故障排查

| 症状 | 原因 | 解决 |
|---|---|---|
| HTTP 页打不开 | IP 不对 / 网络盒没上电 | `curl http://192.168.1.2/` 试；看 `192.168.1.x` 网段 |
| RDT 收不到包 | ①命令字节错（只能用 `0x00`+采样数）②`comm.htm` 里 RDT 被禁用 ③采样数=0 | 先 `--check` 试；去 `comm.htm` 把 RDT Interface 设为 Enabled |
| 数据全是 0 | 没启动流 / 配置选错标定 | 确认发了 `12 34 00 01`；`config.htm` 选对标定 |
| 数值单位不对（差 1~10 倍） | 单位选项是 lbf / kgf 而非 N | `config.htm` 的 Force/Torque Units |
| 状态字非 0 | 某轴饱和（受力超量程） | 看 `decode_status()` 输出；减小受力或换大量程传感器 |
| 读数一直有恒定偏置 | **没置零**（工具自重） | `tare` 服务或 `setting.htm` 设 Bias |
| 包率上不去 | RDT Output Rate 限制 | `comm.htm` 调 RDT Output Rate（1~7000Hz）与 Buffer Size |

```python
import socket, re
pkt = bytes([0x42,0x11,0x00,0x02,0x00,0x00,0x00,0x01])   # GVCP DISCOVERY_CMD
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_BROADCAST, 1); s.settimeout(4)
s.sendto(pkt, ("192.168.1.255", 3956))
data, addr = s.recvfrom(2048)
for x in re.findall(rb"[ -~]{4,}", data):
    print(x.decode())      # 厂商名/型号/版本/序列号
```

# 三、把两者并入现有系统

## 3.1 TF / 坐标系：先解决 base 与 base_link 的坑（已实测）

视觉抓取的**第一步不是相机，是坐标系**。本机实测：

```bash
# 起 TF（需要 /joint_states，见 scripts/start_ur_tf.sh）
bash scripts/start_ur_tf.sh ur10
python3 scripts/check_fk.py
```

实测输出：

```
=== ① TF 算出来的末端位姿 ===
  base      → tool0:  位置 [0.6473, -0.2709, 0.3245]
  base_link → tool0:  位置 [-0.6473, 0.2709, 0.3245]
=== ② 机器人自报的 TCP 位姿（30001，真值）===
     位置 [0.6475, -0.2685, 0.3260]
=== ③ 结论 ===
  base      → tool0 与真值最大偏差: 0.0025 m      ✔ 对得上
  base_link → tool0 与真值最大偏差: 1.2948 m      ✘
```

**结论（血泪教训）**：

1. **机器人自报的 TCP 位姿用的是 `base` 系**（UR 原生基座坐标系）；
2. URDF 里的 `base_link` 相对 `base` **绕 Z 转了 180°**，两者 **X/Y 镜像**；
3. **把相机算出的目标点误用 `base_link` 系，机械臂会跑到反方向去抓** ——
   本机偏差 **1.29 米**，不是"偏一点"，是"完全跑到另一边"。
4. 残差 2.5mm 属正常（标称 URDF vs 出厂标定差异）。

**姿态表示法也要当心**：UR 的 `movel(p[x,y,z,rx,ry,rz])` 里 `rx,ry,rz` 是
**轴角(rotation vector)**，**不是 RPY**！TF 给的是四元数/RPY。
`scripts/ur_arm.py` 提供了转换函数（已用真机数据往返验证，误差 4.4e-16）：

```python
from ur_arm import quat_to_rotvec, rotvec_to_quat, quat_to_rpy, rpy_to_quat
```

实测同一姿态的两种表示：

```
TF 的 RPY   (3.086, -0.069, -1.770)
真机轴角    (1.935, -2.364,  0.000)      ← 同一个姿态！
```

## 3.3 视觉抓取的完整数据流

```
 Mech-Eye 相机
      │  /mechmind/point_cloud        （相机坐标系）
      ▼
 ① 点云处理：分割出目标物体 → 位姿估计（模板匹配 / 分割 / 深度学习）
      │  得到物体位姿 (位置 + 姿态)
      ▼
 ② 坐标变换：camera_link → base
      │  tf2: lookup_transform("base", "camera_link")
      │  ⚠ 务必用 base（不是 base_link）
      ▼
 ③ 生成抓取位姿：在物体位姿上加夹爪偏置，并抬高 H 作为安全高度
      │  姿态转成轴角：quat_to_rotvec()
      ▼
 ④ 复用现有抓放脚本：把位姿喂给 Arm.movel()
      │  scripts/ur_pick_place_full.py 的 poses.json 换成实时算出的位姿
      ▼
 ⑤ 夹爪闭合 + 力传感器确认
         g.close() → OBJ=2 表示夹住（见 docs/04）
         /ft_sensor/wrench 监测碰撞/插装力
```

**要点**：
- 相机固定在外部（**eye-to-hand**）时，`camera_link → base` 是**常量**，
  标定一次即可（这就是"手眼标定"）；
- 相机装在末端（**eye-in-hand**）时，`camera_link → tool0` 是常量，
  而 `tool0` 随臂动——所以**必须靠 TF 链实时换算**，这也是 3.1 节那个坑最危险的地方。

## 3.4 力传感器的两种用法

| 用法 | 做法 |
|---|---|
| **碰撞/接触检测** | 监测 `/ft_sensor/wrench` 幅值，超阈值就停（`movel` 前先 `tare`） |
| **力控装配/插装** | 监测特定方向力，做搜索或柔顺策略；UR 侧也可用 URScript 的 `force_mode()` |
| **抓取成功确认** | 抬起瞬间看 Fz 是否等于物体重量（比 `OBJ` 更定量） |

### 多姿态重力标定

不要把带载工具的某一姿态写入 ATI 硬件 Bias 当作重力补偿。硬件 Bias 保持全 0，
用多个静止姿态联合辨识工具质量、传感器坐标下重心、六维零偏和
`tool0 -> ft_sensor` 旋转：

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
cd ~/UR10

# 只读当前 TCP 并预览 12 个姿态，不会运动
python3 scripts/calibrate_ft_gravity.py

# 人在机械臂旁、手放急停，确认末端旋转空间无障碍后才执行
python3 scripts/calibrate_ft_gravity.py --execute
```

脚本保持 TCP 位置不变，以当前姿态为中心做默认 `±20°` 的低速姿态变化，
每个姿态停稳后从现有 `/ft_sensor/wrench` 采样 1 秒。结果写入
`config/ft_gravity_calibration.yaml`，同时报告力/力矩拟合残差；姿态覆盖不足时拒绝输出。

`/ft_sensor/tare` 仅用于某个固定工作姿态的临时软件去皮，不能替代上述姿态相关的重力补偿。

> UR 控制器**自带** `force_mode()` / `end_force_mode()`（URScipt 内置，见
> `docs/03`），它基于关节电流估计，**不需要外部传感器**——
> 做简单的力保护动作可以先不上 ATI，成本更低。

## 3.5 手眼标定怎么做（适配本机的 CB3 方案）

标准工具是 **[`easy_handeye2`](https://github.com/marcoesposito1988/easy_handeye2)**
（ROS 2 版，硬件无关），用 ArUco 标定板 + 多个机械臂位姿解 `AX=XB`。

**关键点**：easy_handeye2 默认用 MoveIt 自动摆位，但**本机是 CB3、没有 ur_robot_driver
也没有 MoveIt 配置**。它提供了一个 `freehand_robot_movement:=true` 模式——
**不动用 MoveIt，你自己手动摆机械臂，它只负责读 TF 和算标定结果**。这正好适配我们：

```bash
# 1) 源码编译（不在 apt 里）
cd ~/colcon_ws/src
git clone https://github.com/marcoesposito1988/easy_handeye2.git
cd ~/colcon_ws && colcon build --packages-select easy_handeye2

# 2) 装 ArUco 检测（apt 有，已核实）
sudo apt install ros-humble-aruco-ros

# 3) 起标定界面（手动摆位模式）
ros2 launch easy_handeye2 calibrate.launch.py \
    freehand_robot_movement:=true \
    name:=mech_eye_calib \
    tracking_base_frame:=camera_color_optical_frame \
    tracking_marker_frame:=aruco_marker_frame \
    robot_base_frame:=base \
    robot_effector_frame:=tool0
```

# 5. 怎么在网络上找设备

这两台设备都是**自己"喊"出来**的，比翻铭牌、翻文档可靠得多。三个通用手法：

| 手法 | 适用 | 命令 |
|---|---|---|
| **TCP 端口扫描** | 已知服务端口 | 见 `scripts/diagnose.py` 的思路：并发生连 `192.168.1.1-254` 的常见端口 |
| **HTTP 探测** | 有网页服务的设备（ATI 就是这样现形的） | `curl -i http://192.168.1.X/` 看 `Server:` 头 |
| **GVCP 广播发现** | **所有 GigE Vision 相机**（连不同网段也能找到） | UDP 广播到 `255.255.255.255:3956`，见 2.1 节代码 |
| **MAC 厂商查询** | 任何以太网设备 | `curl https://api.macvendors.com/00:16:bd` → `ATI Industrial Automation` |

ATI 就是这样被认出来的：`Server: NET-FT/1.0` + MAC 厂商 `ATI Industrial Automation`
+ 网页标题 `Net F/T Force/Torque Sensor`。
