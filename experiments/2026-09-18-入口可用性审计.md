## 三、不可用/有缺陷的部分（逐条附复现证据）

### 3.1 `start_dashboard.sh --stop` 是**假的**：打印成功但进程不死 ★用户直接踩到

实测：

```bash
bash scripts/start_dashboard.sh --stop     # 输出"已停止所有监控台相关进程"
ss -ltn | grep -E '8080|9090'              # 仍然 LISTEN
ps -eo pid,cmd | grep ros_web_bridge       # 桥仍存活
```

进一步逐信号实测（PID 9659 那次）：

| 手段 | 结果 |
|---|---|
| `kill -TERM` | **无效**，进程存活 |
| `timeout 25`（=SIGTERM） | **无效**，25 s 后进程仍带着 8080/9090 |
| `kill -INT`（=Ctrl-C 那条路） | **无效**，进程存活 |
| `kill -9` | 有效 |

**根因**：`scripts/ros_web_bridge.py:461` 把 `rclpy.spin()` 放在**守护线程**里，主线程跑 asyncio；
而 `rclpy.init()` 默认安装 SIGINT+SIGTERM 处理器（ROS 2 Humble `SignalHandlerOptions.ALL`），
信号被它吃掉、却没有 `rclpy.shutdown()` 的消费方 → 进程永不退出。
所以脚本里的 `cleanup()`（`kill`）、`--stop`（`pkill -f`，即 SIGTERM）、
以及 `docs/10` 承诺的"Ctrl-C 退出并清理"**三条路全部不成立**。

**后果**：残留桥实例永久占着 8080/9090；而且脚本判断"是否已在运行"只靠
`pgrep -f ros_web_bridge.py`（脚本第 ~60 行），**从不校验 :8080 是否真的应答** →
下一次启动会打印"==> 桥已在运行" + 一句成功的地址提示，而页面实际打不开。
这就是"现在这个打不开了"的可复现机制。

**建议的最小修复**（3 处，供你决定是否交给某个会话去做）：
1. 桥改成用 `signal.signal(signal.SIGTERM, ...)` 显式设置 `self._ur_stop` 并 `os._exit`，
   或把 asyncio 放进线程、让 `rclpy.spin()` 回到主线程（rclpy 的信号处理才有效）；
2. 启动前把"是否已在运行"改成**探活**：`curl -sf -m 2 http://127.0.0.1:8080/ >/dev/null`
   成功才算在跑，否则先 `kill -9` 残留再起；
3. `--stop` 用 `pkill -9`（或先 TERM、2 s 后 KILL）并**校验端口已释放**后才打印"已停止"。

### 3.2 相机服务调用**无响应**（⚠️ 需非沙箱终端复核）

实测（今天，两台**新起**的相机节点实例都一样）：

| 调用 | 结果 |
|---|---|
| `ros2 service call /device_info mecheye_ros_interface/srv/DeviceInfo "{}"` | 40 s 无响应 |
| `ros2 service call /capture_color_image ...` | 40 s 无响应 |
| `python3 scripts/validate_mecheye_capture.py`（--timeout 20 与 60） | `TimeoutError: image capture/message timeout` |

同时确认：
- 相机**硬件正常**：日志显示 `按 IP 直连相机成功: 192.168.1.33 (固件 2.5.0)`，
  型号 Mech-Eye PRO XS，SN `RAM35238A3020004`；服务与话题都注册成功
  （`/capture_color_image`、`/mechmind/color_image` 等 6 服务 + 7 话题）。
- **ROS 服务机制本身正常**：本地自检服务（`std_srvs/Trigger`）能 5 s 内找到并在 10 s 内回应。
- 今天 09:56 还留下过一个**不是我这个沙箱启动的** `/device_info` 挂起客户端（`ps` 里没有 bwrap 包装）→
  同样的"无响应"在更早就出现过。
- **但**：我的命令跑在只读 `bwrap` 沙箱里（`touch /var/log/x` → `Read-only file system`），
  相机 SDK 启动时正好报 `Logger: Error: No write permission for directory /var/log/`。
  这是**可能**的干扰因素，所以本条必须在**普通终端**复现确认：

```bash
# 终端 A（普通终端，不要在我的沙箱里）
cd ~/UR10 && source /opt/ros/humble/setup.bash && source ~/colcon_ws/install/setup.bash
ros2 launch ~/colcon_ws/src/mecheye_ros2_interface/launch/start_camera_ur10.py
# 终端 B
cd ~/UR10 && source /opt/ros/humble/setup.bash && source ~/colcon_ws/install/setup.bash
python3 scripts/validate_mecheye_capture.py
```

若普通终端仍超时 → 这是**真实的链路故障**，会直接挡住棋盘格标定与会话级视觉流程，
现象/日志/复现命令应写进 `experiments/`；若普通终端正常 → 只是我的沙箱限制，忽略本条。

### 3.3 文件权限卫生（同用户跑没事，换用户/容器会坏）

```
600  web_dashboard/index.html, app.js, style.css        # 组/他人不可读
711  scripts/ 下 25 个脚本（ati_netft_node.py, ros_web_bridge.py, start_dashboard.sh, diagnose.py ...）
```

0600 的网页资源 + 0711 的脚本：同一用户（jx）运行没问题，
但**以其他用户/容器/root 启动**（例如以后做成服务）会读不到文件。
建议统一 `chmod 644`（脚本 755）。

### 3.4 `ros2 node list` 返回空（排查时会误判"节点没起"）

实测：`ros2 node list` 空，但 `ros2 topic list` 有 12 个话题，
桥/ATI/相机节点进程都在。排查时**不要**用 `ros2 node list` 判断节点是否启动；
用 `ros2 topic list`、`ros2 service list` 或 `ps`。
