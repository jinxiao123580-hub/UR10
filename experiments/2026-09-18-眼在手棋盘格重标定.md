## 三、本轮工具改动（补 09-17 的最大证据缺口）

09-17 只存 `image.png` + `corners.png` + 摘要 JSON：76 帧机器人状态被压成 4 个数，且**没有点云**
⇒ 无法离线复核。本轮改如下。

### 3.1 `scripts/collect_handeye_sample.py`

- **新增 `robot_frames.json`（默认写）**：完整 30003 帧日志（`monotonic_s / q_rad / tcp_pose / tcp_velocity`），
  不再只留均值。`--no-robot-frames` 可关闭。
- **新增 `--save-cloud`**：额外触发 `/capture_point_cloud`，把**原始组织化点云**（相机系 `camera_xyz_m`，float32）
  连同 `k / d / corners_px / camera_from_target / base_from_tool0 / inner_corners / square_size_m`
  一起写成 `cloud.npz`。为此把 payload 构造抽成模块级 `build_cloud_payload()` / `save_cloud_npz()`，
  使离线自检能复用同一 schema（不复制粘贴）。
- 每个样本目录现在包含：`image.png`、`corners.png`、`robot_frames.json`、`cloud.npz`、`sample.json`。

### 3.2 `scripts/solve_handeye_checkerboard.py`

- **新增 `observability()`**：给出 AX=XB 设计矩阵条件数。旋转部分用
  `R_A X_R = X_R R_B`（`R_A = rot(A_i⁻¹A_j)`、`R_B = rot(B_i B_j⁻¹)`）列堆叠成
  `M = kron(I, R_A) − kron(R_Bᵀ, I)`，报奇异值、`rank@1e-9`、`null_space_gap = σ₈/σ₉`、
  `condition_number`；平移部分用 `(I − R_A)t_X = …`，其条件数有限且有意义；
  另报**相对旋转轴各向同性** `min_over_max`（≈0 表示所有相对旋转共轴 ⇒ 退化）。
- **新增 `--holdout-ids`**：留出集可以用样本 id 显式钉死（默认仍是"最后 N 个"），
  使划分可复现、与排序无关；少于 5 个直接报错。

### 3.3 新增 `scripts/analyze_handeye_closure.py`（独立验收）

与求解器分离：求解器产出候选，本脚本**审判**候选。给定冻结 yaml，对每个接受样本重算
`base_from_target = base_from_tool0 · tool0_from_camera · camera_from_target`，报

- **固定棋盘格闭环**：板原点位置散布（RMS/max/xy span）、板姿态散布（整体 + 法向）、
- **54 个角点的世界坐标散布**（RMS/p95/max，逐角点最大），
- 重跑样本自带的门禁（重投影 px、静止性 mm/deg、角点数），
- **原始点云逐角点交叉校验**：用 K/D + 角点像素在 `cloud.npz` 的深度通道上取邻域中值，
  与 PnP 期望的角点 xyz 比对 —— **不经过手眼变换**，因此是独立于标定的一条几何证据。

### 3.4 新增 `scripts/handeye_pose_advisor.py` + `scripts/check_handeye_plan_observability.py`

采集期间机器人必须静止、且由现场用示教器点动（禁止电脑端流式 IK）。为让 26 个位姿不是盲点，
新增点动导航：把"距离/倾角/方位角/滚转"四个量 ↔ `camera_from_target` 双向映射，
输出**目标 TCP 位姿表**（示教器可读的 x y z rx ry rz）、覆盖率报告与"下一个空槽位"。

### 4.2 点动导航自检 — `handeye_pose_advisor.py --self-test`

**7/7 PASS**

| 用例 | 结果 |
|---|---|
| 球坐标往返 < 1e-6 | ✅ |
| **`solvePnP` 的 `camera_from_target` 必须把靶标放在相机前方（+z）且模长=距离** | ✅ |
| **流水线约定下的参数还原 < 1e-6** | ✅ |
| 计划 26 槽 | ✅ |
| 每主壳 8 个方位 | ✅ |
| 倾角随壳递增 | ✅ |
| 覆盖率匹配器能把按计划构造的数据集**满槽填满** | ✅ |

**这里抓到一个真 bug（本轮最有价值的代码修正）：** 前三项里的前两项是本轮**补加**的。
原先只有一个"往返 < 1e-6"自检，它**只验证自洽**——把平移语义整个反向也能通过。实际写出来的
`camera_from_target_from_spherical` 把 `transform[:3,3]` 当成"相机在靶标系的坐标"，而流水线里
（`solvePnP` 的 tvec）`camera_from_target[:3,3]` 的含义是**"靶标原点在相机系的坐标"**，两者相反。

- 影响面：**计划的绝对 TCP 位姿一直是正确的**（`base_from_target @ target_from_camera` 在数学上
  与约定无关，测试证实修复前后计划的 26 个 TCP 目标**逐位不变**）；错的是**覆盖率报告与 `--live`**
  这些把流水线 `camera_from_target` 直接喂回球坐标函数的地方——它会把一个真实样本读成
  `tilt 173.8°`（应为 28.0°），从而给出完全错误的"下一个空槽位"。
- 修法：函数按真实语义改名 `target_from_camera_from_spherical` / `spherical_from_target_from_camera`，
  所有持有流水线 `camera_from_target` 的调用点先取逆；并补上上面两条**钉住约定**（而非只验自洽）的自检。
- 验证：真实冒烟样本修复后读作 `dist 0.386 m / tilt 28.0° / azimuth 184.6°`（人工目测点位，合理）。

### 4.3 计划可观性门禁 — `outputs/handeye/plan-observability-gate.json`

命令：`python3 scripts/check_handeye_plan_observability.py --reference <参考样本>`

对每一种滚转模式，用参考样本预测出整套 26 个位姿，再跑求解器同款的可观性判据：

| 滚转模式 | rank | null_space_gap / cond | 轴各向同性 | 法兰最低 z | 不同滚转值 | 方位扇区 |
|---|---|---|---|---|---|---|
| design（设计滚转 ±25/±45°） | 8 | exact (floor) | **0.107** | **0.079 m** | 4 | [4,3,3,3,4,3,3,3] |
| clearance（取法兰最高的滚转） | 8 | exact (floor) | 0.032 | **0.255 m** | 3 | [4,3,3,3,4,3,3,3] |

`rank = 8` 正是手工眼齐次系统的良态值；`null_space_gap`/`cond` 显示 "exact (floor)" 是因为
合成数据无噪声、零空间在双精度下精确（不是病态）——工具会把这种情况显式标注为
`null_space_at_numerical_floor`，避免把"精确零空间"误读成天文数字的条件数。
对照组：09-17 的**真实**数据 `rank 9`、`gap 37.2`、`cond 89.7`、`σ₉/σ₁ = 1.1e-2`（远离噪声底），
说明这两类数字含义不同、工具能区分。

**决策：采用 clearance 模式。** 依据是实测而非偏好——09-17 那套**物理上成功采过**的 20 个位姿，
法兰高度实际范围是 **0.202–0.430 m**（§六）。design 模式会把法兰压到 0.079 m，比历史上任何一次
都低 12 cm，属真实避障风险；而它换来的轴各向同性提升（0.107 vs 0.032）不是"退化 vs 非退化"的
差别（两者都远离 0，且 8 方位 × 3 倾角的铺开本身已提供多轴激励）。

## 十、能不能用脚本把机械臂直接开到目标位姿？（离线数值门禁层，只读）

### 10.6 网络中断的真正原因（现场更正）

先前归因为"网线被碰掉"。现场更正：**是机械臂拉到了自己的线缆、受力触发保护停**
（线缆是相机/力传感器那束，随相机一起运动）。这条更正很重要，因为它把"偶发网络故障"
改判为**一个已发生的、由机械臂自身运动造成的硬件事件**。

⇒ 影响：原先"台面上只有 ≤50 mm 物体"的避障论证**不覆盖线缆**，必须单独处理。见 §十一。

### 11.2 查出的执行器 bug：到位判据只查位置、不查姿态

**纯转动段的 TCP 线速度天然≈0**，所以每个 `reorient` 段都在 0.0–0.2 s 内被判"到位"
（实测姿态只变了 0.00009 rad），下一条 `movel` 在转动未完成时就发出，两条运动叠加。

修法：到位判据改为**位置 + 姿态 + 线速度 + 角速度四项同时满足**
（`POSITION_TOLERANCE_M=1.5 mm`、`ROTATION_TOLERANCE_RAD=0.006 rad`、
`SETTLE_SPEED=0.003 m/s`、`SETTLE_ANGULAR_SPEED=0.02 rad/s`），并加**停滞检测**。
`pose_error()` 已单元验证（同一姿态 / 纯平移 / 纯转 90° / 转 1.7 rad 四种情形全对）。

同时修正第二个不忠实之处：执行器原本按槽位号顺跑，而门禁验证的是**特定访问顺序**
（关节空间最近邻 + 逐槽救援滚转）。已改为**逐段重放门禁 JSON 里的段列表与顺序**，
执行器不再自行重算路径。

### 11.3 关键发现：恒定滚转会把腕关节拧死（线缆绞紧机制）

对门禁轨迹逐段求 IK 并统计**腕关节 J6 的真实转角**：

| 方案 | J6 净变化 | J6 累计行程 | J6 范围跨度 | 最大单段 |
|---|---|---|---|---|
| **原计划（26 槽全部滚转 190°）** | −144.3° | **2140.3°** | 315.5°（**顶到 −360° 限位**） | **191.6°** |
| 360° 绝对锚定 J6 | +296.4° | 957.5° | 405.1° | 95.1° |
| **180° 半圈 + 绝对锚定** | +296.4° | 983.6° | **358.3°** | **72.7°** |

⇒ **原计划会把腕关节累计拧 6 圈、并顶到 J6 硬件限位**，这正是勒紧相机线缆的机制，
与现场那次"机械臂拉到自己线缆受力触发保护停"吻合。

改版措施与效果：

1. **滚转目标从"法兰最高"改为"腕部连续"**（`--roll-objective wrist`），
   并以**绝对锚定**（所有位姿的 J6 贴近起始 J6）而非增量锚定——增量锚定是顺序相关的，
   而滚转优化顺序与门禁执行顺序不一致，收益会被抵消（实测净绞紧仍 +222°）。
   滚动集合由恒定 {190°} 变为 95–220° 散开。
2. **法兰下限提到 0.25 m**（沿用 `ur_relative_movel.py` 自身的硬门禁），
   防止"为连续性牺牲避障"：实测法兰 0.2502–0.4853 m，无一个低于 0.25 m。
3. **方位跨度收到 180°**（`--azimuth-span-deg 180`）：仍是 8 个不同方向，满足
   "朝向至少 3 个方向"的要求，但单段最大腕转从 95.1° 降到 **72.7°**、跨度降到 358.3°。

结果：累计行程 −55%、最大单段 −62%、**不再顶 J6 限位**。
**但净绞紧仍约 +296°**，即"把腕子拧大半圈"这件事在模型层面没有被消除。

### 11.4 必须说清的模型局限

上述 J6 数字是**标称 URDF 的 IK 推算**，不是控制器实际关节角：同一个笛卡尔位姿有多个
IK 解，控制器按自己的准则选分支。所以这些数字只能作**相对比较**，不能当实测。

⇒ 因此给执行器加了**实际关节角记录**（`run_move_plan.py` 的 `actual_wrist` 块：
从 30003 的 `q_actual` 直接读 J6 的起点/终点/净变化/累计行程/跨度）。
**真实结论必须来自实跑数据**，做法是分段执行（`--first-slots N` 取访问顺序的**前缀**，
不能用 `--slots` 任意子集，否则起点与门禁链不符——执行器已加该校验并实测拒绝过一次）。
