# 2026-09-18 相机采集链路复核：不是链路故障，是 DSH 沙箱私有 /dev/shm 打断 FastDDS 共享内存传输

## 结论摘要

1. **相机采集链路本身完全正常**。带 `FASTDDS_BUILTIN_TRANSPORTS=UDPv4` 后：
   `/device_info` 正常应答、`scripts/validate_mecheye_capture.py` 全流程通过、
   `scripts/check_handeye_checkerboard.py` 能取图并落盘。
2. **2026-09-18 入口可用性审计 §3.2 的"相机服务无响应"是伪故障**：根因是执行该命令的
   DSH 沙箱把 `/dev/shm` 做成**每次 bash 调用私有的 tmpfs**，Fast DDS 进程间共享内存
   传输因此必然失效——发现（UDP 多播）仍正常，所以话题/服务都能被列出来，但**用户数据
   永远送不到**。两个进程即使在同一个沙箱内也互相收不到消息。
3. 因此 §3.2 里"`ros2 service call /device_info` 40 s 无响应"的现象，**不能**归因于相机、
   SDK、IP 直连或 ROS 服务机制；它与 `/var/log` 只读也**无关**（下一条）。
4. `/var/log` 只读确实会发生（SDK 打印 `Logger: Error: No write permission for directory /var/log/`），
   但它**不阻塞**任何功能：本记录中所有成功采集都发生在 `/var/log` 仍只读的沙箱里。

## 判别过程（每步都可复现）

### 第 1 步：先按原样复现现象

沙箱内 `/var/log` 只读（与 §3.2 同条件）：

```bash
touch /var/log/.dsh_test    # → Read-only file system
```

按文档流程启动相机（沙箱内，未设任何 Fast DDS 变量）：

```bash
ros2 launch ~/colcon_ws/src/mecheye_ros2_interface/launch/start_camera_ur10.py
```

启动日志与 §3.2 完全一致：`No write permission for directory /var/log/`、
`Failed to obtain the IP address of the computer Ethernet port...`（多网卡已知警告）、
`按 IP 直连相机成功: 192.168.1.33 (固件 2.5.0)`、型号 `Mech-Eye PRO XS`、
SN `RAM35238A3020004`。`ss -tnp` 显示 `192.168.1.10:41776 → 192.168.1.33:5577 ESTAB`。

复现超时：

| 调用 | 结果 |
|---|---|
| `ros2 service call /device_info ... "{}"` | 30 s 无响应 |
| `ros2 service call /get_int_parameter ...` | 25 s 无响应 |
| `python3 scripts/validate_mecheye_capture.py` | `TimeoutError: image capture/message timeout after 20.0s` |

### 第 2 步：分离"节点卡死"与"传输不通"

决定性观察：**连原生 rclpy 服务也无响应**：

```bash
ros2 service call /mechmind_camera_publisher_service/describe_parameters \
  rcl_interfaces/srv/DescribeParameters "{names: ['save_file']}"   # 20 s 无响应
```

`describe_parameters` 由 rclpy 内部实现、完全不碰 SDK。它可以排除"SDK 采集卡住"，
但也还不能排除"沙箱"。进程侧取证：相机进程存活、25 线程、CPU 0.2%、`wchan=0`
（睡眠在用户态，不是在内核等待），`MultiThreadedExecutor` 本应让某个回调阻塞时其它
回调仍能被服务——**却一个都不响应**。

### 第 3 步：在沙箱内自建最小服务做对照（关键一步）

在**同一个沙箱**里起一个 trivial 的 `std_srvs/Trigger` 服务提供者，另一个 bash 调用做客户端：

```python
# 提供者：只 create_service + spin，不碰任何硬件
print('wait_for_service ->', c.wait_for_service(timeout_sec=15.0))   # → True，0.0 s
# 调用后 10 s 内 future 始终未完成
# 同一对进程间的 std_msgs/String 话题：收到 0 条
```

⇒ **发现正常、数据不达**，而且这与相机毫无关系：连两个纯 Python 节点之间也这样。
这把根因从"相机/SDK/服务机制"彻底移到"沙箱的进程间传输"。

### 第 4 步：定位到 /dev/shm

```bash
grep shm /proc/mounts        # tmpfs /dev/shm tmpfs ro,nosuid,nodev,inode64 0 0
echo x > /dev/shm/dsh_probe.txt   # 本次调用内可写、可读
ls /dev/shm/dsh_probe.txt         # 下一次 bash 调用：No such file or directory
```

⇒ `/dev/shm` 在沙箱内是**每次调用重新挂载的私有 tmpfs**。Fast DDS 在同一主机上默认优先
用共享内存传输（builtin transport `SHM`），它靠 `/dev/shm` 里的段名匹配；两个持有**不同
`/dev/shm`** 的进程会匹配上名字却共享不到内存，于是建立不了数据通道，而基于 UDP 多播的
发现（discovery）照常工作。这精确解释了"服务列得出来、`wait_for_service` 为 True、
调用却永不返回"。

### 第 5 步：绕过并验证

把 Fast DDS 的传输限制为 UDP，禁用 SHM：

```bash
export FASTDDS_BUILTIN_TRANSPORTS=UDPv4
```

同一对最小服务/话题立刻正常：

|---|---|---|

| 收到话题消息数 | 0 | **24** |

## 对现场操作的要求

- 在 DSH 沙箱里跑**任何** ROS 2 话题/服务通信（相机节点、采集脚本、求解无关）都必须：
  ```bash
  export FASTDDS_BUILTIN_TRANSPORTS=UDPv4
  ```
  发起端与响应端**都**设，最省事。
- 这是**沙箱绕行**，不是仓库缺陷，也不是需要修的东西：普通终端（非 bwrap）里
  `/dev/shm` 是正常的，文档里原有的启动流程照旧有效。
- 反过来也成立：**以后在沙箱里遇到"ROS 服务/话题无响应"，先怀疑这条**，
  `export FASTDDS_BUILTIN_TRANSPORTS=UDPv4` 是最便宜的判别实验（10 秒出结论）。
- `/var/log` 只读（`Logger: Error: No write permission for directory /var/log/`）
  **不影响**任何功能，不必为它去改权限。
